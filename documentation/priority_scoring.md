# Priority Scoring

## Purpose
The Priority Scoring system was added to help users quickly identify the most urgent customer feedback requiring attention. Rather than relying on raw AI confidence scores alone, the priority system combines the sentiment classification and the confidence score into a single deterministic metric.

This allows businesses to sort and filter feedback by severity, ensuring that highly confident negative reviews are addressed first.

## Methodology
The Priority Scoring engine is a **deterministic, rule-based system**. It does not use LLMs, RAG, or any secondary AI model. It calculates priority based strictly on the primary machine learning outputs (Sentiment and Confidence).

### Inputs Used
1. **Sentiment**: `Positive`, `Neutral`, or `Negative`.
2. **Confidence**: A float between 0.0 and 1.0 generated by the underlying Scikit-learn model.

### Exact Formula
The priority score is a normalized value between `0` and `100`:
- **Negative Sentiment**: `Round( 50 + (confidence * 50) )`
  - *Range: 55 to 100*
- **Neutral Sentiment**: `Round( 50 - (confidence * 20) )`
  - *Range: 30 to 48*
- **Positive Sentiment**: `Round( 30 - (confidence * 20) )`
  - *Range: 10 to 28*

### Priority Levels
The 0-100 score is then mapped into human-readable priority levels:
- **Critical**: `Score >= 80`
- **High**: `Score 60 - 79`
- **Medium**: `Score 40 - 59`
- **Low**: `Score < 40`

### Example Calculations
- A **Negative** review with `90%` confidence: `50 + (0.9 * 50) = 95` => **Critical**
- A **Negative** review with `40%` confidence: `50 + (0.4 * 50) = 70` => **High**
- A **Neutral** review with `80%` confidence: `50 - (0.8 * 20) = 34` => **Low** (Strongly neutral)
- A **Positive** review with `90%` confidence: `30 - (0.9 * 20) = 12` => **Low**

## Technical Implementation

### Database Changes
No new columns were needed. The existing `reviews.priority_score` column (FLOAT) was repurposed to store the 0-100 score instead of its legacy logic. 
A schema migration (`init.js`) was added to automatically backfill the 0-100 score for all existing historical feedback.

### API Changes
- **`GET /api/feedback`**: Added `?priority=Critical|High|Medium|Low` parameter. The filtering is executed at the SQL level (e.g. `AND priority_score >= 80`) to ensure pagination remains perfectly accurate.
- **`GET /api/analytics/trends`**: Aggregates `critical` and `high` priority counts using `SUM(CASE WHEN priority_score >= ...)` directly in the MySQL database engine.

### Frontend Changes
- **Dashboard**: Two new metrics cards were added for "Critical Priority" and "High Priority". These pull from the time-filtered `trends` analytics endpoint.
- **Feedback List**: A new dropdown allows users to filter by priority level.
- **Feedback Rows**: A color-coded Priority Badge (Red/Orange/Yellow/Gray) now dynamically renders in the "Intelligence" column based on the row's `priority_score`.

### Smart Alert Integration
The Pulse Smart Alert system (Resend API) historically relied on an `alert_threshold` setting (0 to -1 polarity). The new priority logic preserves this behavior perfectly. 
A review triggers a critical email alert if it is either inherently **Critical (score >= 80)** OR if its polarity breaches the user's custom threshold setting.

### Tenant Isolation
All priority-related database operations (fetching counts for the dashboard, filtering lists, CSV uploading) are wrapped inside the `req.tenantId` middleware bounds. Priority data is never cross-contaminated between organizations.

## Testing Performed
- Validated rule-based formula limits to ensure scores strictly fall into the intended 0-100 boundaries.
- Tested CSV Bulk Upload to ensure all hundreds of reviews accurately calculate their priority score in a fraction of a second without triggering Resend rate limits.
- Tested backend migration script to verify that existing databases are upgraded correctly without data loss.
- Tested "0 Critical" empty states on the Dashboard.
